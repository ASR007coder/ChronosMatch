# ChronosMatch — Matching Rules

## 1. Purpose

This document defines the matching rules, order-book behavior, validation requirements, and public interface for the ChronosMatch matching engine.

The matching engine processes incoming limit orders, matches compatible buy and sell orders, generates trade records, and stores any unfilled quantity in the order book.

The implementation must follow these rules consistently in both the Python engine and the planned Cython engine.

## 2. Order Representation

Orders use the `Order` model defined in `backend/engine/models.py`.

| Field | Type | Description |
|---|---|---|
| `order_id` | Integer | Unique order identifier; uniqueness is the producer's responsibility. |
| `sequence` | Integer | Starts at 1 and increases strictly for each processed order. |
| `side` | Integer | `BUY = 0`, `SELL = 1`. |
| `price` | Integer | Limit price represented in paise; floating-point prices are not allowed. |
| `quantity` | Integer | Number of units; must be positive. |
| `timestamp_ns` | Integer | Informational timestamp; not used to determine priority. |

The engine must not silently modify an order's price, quantity, side, or sequence.

## 3. Order Types and Scope

The engine supports:

- Limit orders only.
- A single instrument.
- Buy and sell orders.
- Partial fills.
- Multiple trades from a single incoming order.
- Resting unfilled quantities in the order book.

Order cancellation, order modification, and multi-instrument matching are outside the scope of Week 1.

## 4. Price-Time Priority

The engine follows price-time priority.

### Buy orders

- A higher buy price has priority over a lower buy price.
- At the same price, the order received earlier has priority.
- Sequence order determines arrival priority.

### Sell orders

- A lower sell price has priority over a higher sell price.
- At the same price, the order received earlier has priority.
- Sequence order determines arrival priority.

The order book must preserve FIFO order among resting orders at the same price level.

## 5. Matching Conditions

An incoming order matches against the best available order on the opposite side.

### Incoming buy order

A buy order can match when:

`incoming_buy_price >= best_ask_price`

The engine consumes the lowest available ask price first.

### Incoming sell order

A sell order can match when:

`incoming_sell_price <= best_bid_price`

The engine consumes the highest available bid price first.

Matching continues while the incoming order has remaining quantity and the best opposite-side price satisfies the crossing condition.

## 6. Trade Execution Price

Every trade executes at the resting order's price, not the incoming order's price.

Examples:

- A resting sell order at ₹100.00 matched by a buy order with a limit price of ₹105.00 executes at ₹100.00.
- A resting buy order at ₹100.00 matched by a sell order with a limit price of ₹95.00 executes at ₹100.00.

Prices are stored as integer paise. For example, ₹100.00 is represented as `10000`.

## 7. Partial Fills and Remaining Quantity

The engine must support partial fills.

For each match:

1. Calculate the executable quantity as the smaller of the incoming order's remaining quantity and the resting order's remaining quantity.
2. Generate a trade for that quantity.
3. Reduce the remaining quantity of both orders accordingly.
4. Remove a resting order when its remaining quantity becomes zero.
5. Continue matching if the incoming order still has quantity remaining.

If the incoming order cannot be fully filled, its remaining quantity rests in the order book at its original limit price.

The engine must never create a trade with zero or negative quantity.

The following quantity invariant must hold:

`original_quantity = total_filled_quantity + remaining_quantity`

## 8. Trade Record

Each generated trade is represented by the following tuple:

`(trade_id, buy_order_id, sell_order_id, price, quantity, sequence)`

| Field | Description |
|---|---|
| `trade_id` | Unique trade identifier generated by the engine. |
| `buy_order_id` | Identifier of the buy order involved in the trade. |
| `sell_order_id` | Identifier of the sell order involved in the trade. |
| `price` | Execution price in integer paise. |
| `quantity` | Quantity executed in this trade. |
| `sequence` | Sequence number of the incoming order that caused the trade. |

Trade identifiers start at 1 and increase for each generated trade.

A single incoming order may generate multiple trade records.

## 9. Validation and Error Handling

Invalid orders must be rejected rather than silently modified.

The engine must reject:

- A side other than `BUY = 0` or `SELL = 1`.
- A price less than or equal to zero.
- A quantity less than or equal to zero.
- A sequence number less than or equal to the last successfully processed sequence number.
- Invalid field types, including booleans where integers are required.

Invalid orders should raise `ValueError` for invalid order values and sequence ordering. The implementation must define and test the appropriate exception for invalid field types.

A rejected order must not change:

- The order book.
- The last processed sequence number.
- The processed-order counter.
- The trade counter.
- The next trade identifier.

Sequence numbers must increase strictly, but gaps are allowed. Detecting missing sequences is the responsibility of the pipeline, not the matching engine.

Duplicate order IDs are not checked by the engine in Week 1. Producers must ensure that order IDs are unique.

## 10. Public Engine Interface

The matching engine exposes the following interface:

```python
from backend.engine.matching_engine import MatchingEngine

engine = MatchingEngine()

# Fast path: returns plain trade tuples
trades = engine.submit(
    order_id,
    side,
    price,
    quantity,
    sequence,
)

# Convenience API: accepts an Order object and returns Trade objects
trades = engine.submit_order(order)

# Read-only market views
bids, asks = engine.depth(5)
best_bid = engine.best_bid()
best_ask = engine.best_ask()

# Counters
orders_processed = engine.orders_processed
trades_executed = engine.trades_executed
```

The pipeline should use `submit()` on the hot path.

The planned Cython implementation must preserve the same public API and matching behavior.

## 11. Order Book Invariants

The following invariants must always hold:

1. Every resting order has positive remaining quantity.
2. Fully filled orders are removed from the book.
3. Orders at the same price level remain in FIFO order.
4. The best bid is the highest available buy price.
5. The best ask is the lowest available sell price.
6. Every trade satisfies the crossing condition at execution time.
7. Every trade has positive quantity.
8. A trade cannot execute more quantity than either participating order has remaining.
9. Filled quantity plus remaining quantity equals the original incoming quantity.
10. Rejected orders leave the engine's state unchanged.

## 12. IPC Protocol Compatibility

The engine receives orders through the IPC pipeline.

The agreed binary order record is exactly 64 bytes and uses the little-endian format:

`<QQqQIB27x`

The six decoded fields are:

`(order_id, sequence, price, timestamp_ns, quantity, side)`

The protocol implementation and its validation rules are maintained separately in `backend/ipc/protocol.py`.

The simulator, producer, consumer, and matching-engine integration must agree on field order, integer units, and side values. Changes to the binary format require team agreement.

## 13. Required Test Scenarios

The matching engine must be tested against the following scenarios.

1. **Non-crossing order:** An order does not cross and rests in the book.
2. **Exact fill:** An incoming order fully consumes a compatible resting order.
3. **Partial fill:** An incoming order consumes only part of a resting order.
4. **Multiple fills:** One incoming order matches multiple resting orders.
5. **Price priority:** The best-priced eligible resting order is consumed first.
6. **FIFO priority:** At the same price, the oldest resting order is consumed first.
7. **Invalid orders:** Invalid side, price, quantity, sequence, and field types are rejected.
8. **Incoming sell:** A sell order consumes the highest eligible bids first.
9. **Unfilled remainder:** Any unfilled quantity rests at the incoming order's limit price.
10. **State preservation:** Rejected orders do not alter the order book, counters, sequence state, or trade identifier.
11. **Depth and best prices:** Market-depth results and best bid/ask remain correct after matching.
12. **Sequence gaps:** Increasing but non-consecutive sequences are accepted by the engine.

## 14. Out of Scope

The following are not part of the Week 1 matching-engine contract:

- Order cancellation and modification.
- Duplicate order-ID detection.
- Missing-sequence detection.
- Multi-instrument order books.
- Changes to the agreed IPC binary format.

## 15. Completion Criteria

The matching-engine contract is ready for implementation when:

- The team agrees on the matching rules.
- The Python engine follows the documented public API.
- The required deterministic tests pass.
- Invalid orders leave the engine state unchanged.
- The IPC pipeline uses the agreed 64-byte order format.
- The Python and Cython implementations are expected to produce equivalent results.

This document defines the intended behavior. Completion must be verified through tests before the engine is considered fully compliant.
